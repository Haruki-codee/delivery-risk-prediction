# Olist Delivery Risk Intelligence

End-to-end analytics and machine-learning project built from the supplied Olist e-commerce CSV datasets. It predicts whether a **delivered order** arrived after its estimated delivery date, ranks orders by late-delivery risk, and provides a Streamlit dashboard.

## Project capabilities

1. Data extraction and quality checks (row counts, duplicate rows, missingness).
2. PostgreSQL schema and reusable SQL analysis queries.
3. Exploratory analysis and descriptive statistics.
4. Order-level feature engineering from orders, items, payments, products and customers.
5. Logistic Regression, Random Forest and XGBoost (XGBoost is optional at runtime).
6. Evaluation using ROC-AUC, PR-AUC, precision, recall, F1, confusion matrices and classification reports.
7. Delivery-risk queue ranked by predicted late probability.
8. Streamlit dashboard with overview, risk queue, model comparison, explainability and quality tabs.
9. README, dependency list and GitHub-ready structure.

## Target definition and important caveats

- Target: `is_late = 1` when `order_delivered_customer_date` is later than `order_estimated_delivery_date`.
- Only rows with both actual and estimated delivery timestamps are included in supervised training. Orders not yet delivered or missing either timestamp are excluded.
- The actual delivery timestamp and the derived delivery delay are **not** used as model predictors.
- This is a retrospective prediction based on fields available in the historical extract. The `carrier_handoff_hours` feature is available only after carrier handoff; for a true pre-dispatch intervention, remove post-purchase/post-handoff features and retrain.
- Review scores/comments are intentionally excluded because they are generally post-delivery and would leak outcome information.
- Historical Olist data is observational. Model associations are not causal claims. Risk scores should support human review, not automatically penalize sellers or customers.

## Setup

Python 3.10+ recommended.

```bash
python -m venv .venv
# Windows: .venv\\Scripts\\activate
# macOS/Linux:
source .venv/bin/activate
pip install -r requirements.txt
```

## Run the pipeline

From the repository root:

```bash
python -m src.pipeline
python -m src.eda
python -m src.explain
streamlit run app.py
```

The training pipeline writes:
- `data/processed_orders.csv`
- `reports/data_quality_summary.csv`
- `reports/model_metrics.csv`
- model-specific classification reports and confusion matrices
- `reports/test_predictions.csv`
- `artifacts/*.joblib` and `artifacts/model_metadata.json`

The optional SHAP step writes `reports/shap_summary.png` when SHAP supports the installed model/library combination.

## PostgreSQL

1. Create a database, e.g. `olist_analytics`.
2. Run `sql/schema.sql` in that database.
3. Import each raw CSV into its corresponding `olist` table using pgAdmin's Import/Export UI or `\\copy` from `psql`.
4. Run `sql/analysis.sql`.

The project keeps CSV processing independent from PostgreSQL so it can be run locally without database credentials. For production, use environment variables and a managed secret store; never commit passwords.

## Model evaluation

Do not select a model from accuracy alone. Compare ROC-AUC and PR-AUC, then inspect precision/recall at the operational threshold. If only a limited number of orders can be investigated, evaluate precision@K and recall@K and choose a threshold based on intervention capacity and costs.

## GitHub publishing

The ZIP includes the supplied CSVs for reproducibility. Before publishing publicly, check the dataset license/redistribution terms and consider removing `data/raw/` if you do not want to redistribute the source data. Do not commit secrets, database credentials, or customer-identifying information.

## Reproducibility

The split uses a fixed random seed (`42`). Model results may vary slightly across library versions and hardware. The project is a portfolio/demo baseline, not a production-certified delivery system.
